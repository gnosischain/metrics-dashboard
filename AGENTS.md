# AGENTS.md — metrics-dashboard

The public Gnosis metrics dashboard: a React + Vite single-page app plus Vercel serverless functions that run each card's SQL against the ClickHouse `dbt` schema; one card = `src/queries/<id>.js` + `api/queries/<id>.json` + an entry in `public/dashboards/<sector>.yml`.
The rule that matters most: **the SQL you edit is not the SQL that runs** — production executes the committed `api/queries/<id>.json` (api/metrics.js:110-133; vercel.json:10), which only the manual `pnpm run export-queries` regenerates; neither `pnpm build` nor Vercel runs it (package.json:47,52; vercel.json:4).

## Where this runs (production)

**Vercel only.** The repo has no Dockerfile, Terraform, Kubernetes manifest or CI workflow (repo root listing); `.github/` holds only CODEOWNERS (.github/CODEOWNERS:1).
Vercel runs `pnpm build` and serves `build/` with `framework: null` (vercel.json:4-6; vite.config.ts:148-150).

**Deploys are started by a person.** The repo documents only `vercel --prod` from a machine linked to the Vercel project (README.md:386-395); the link lives in `.vercel/`, which is gitignored, so it exists per machine (.gitignore:27).
The public operations runbook says a push to `main` redeploys and warns that `vercel --prod` ships the uncommitted working tree (cerebro-docs `docs/operations/runbooks/consumers-stale.md:73`).
That Git trigger is Vercel project configuration, not repo content: treat every merge to `main` as a production deploy. Nothing deploys on a schedule. Environment variables live in the Vercel project settings (README.md:397-412).

**Functions.** Every `api/**/*.js` is a function with `maxDuration: 60` that bundles only `api/queries/*.json` (vercel.json:7-12). Every handler answers an `OPTIONS` preflight with 200, then returns 401 unless header `X-API-Key` equals env `API_KEY` (api/metrics.js:284-295; api/test.js:9-20; api/account-portfolio-search.js:313-323; api/validator-explorer-search.js:69-79; api/account-portfolio-overview.js:31-41; api/single-value-api.js:7-18).

**Data source.** ClickHouse over HTTP: axios POST, basic auth, SQL in the `query` URL parameter, `database` from `CLICKHOUSE_DATABASE`, `default_format=JSONEachRow`, 55 s timeout (api/cron.js:204-217).
Env names: `CLICKHOUSE_HOST` (required, else "Missing ClickHouse connection details"), `CLICKHOUSE_PORT`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`, `CLICKHOUSE_DATABASE` (api/cron.js:182-196).
Card SQL names relations `dbt.<model>`; when `CLICKHOUSE_DBT_SCHEMA` is set to another valid name, every `\bdbt\.` (case-insensitive) is rewritten to it, otherwise the SQL is sent unchanged (api/cron.js:11-34,199).
The models come from dbt-cerebro, which builds into the schema named by its own `CLICKHOUSE_DATABASE` (dbt-cerebro `profiles.yml:6`). Nothing ties the two settings together.
**Owner:** `@gnosischain/gnosis-analytics` owns every path (.github/CODEOWNERS:1).

## Hazards

- **Two copies of every query.** The `.js` is source; the `.json` is what runs. A file whose `id:` or `query:` key is quoted (`"id":`) is skipped by the exporter (scripts/export-queries.js:78-84) and its JSON silently freezes. On 2026-09-24 the 32 files written that way were converted to bare keys and re-exported; two of them had been serving stale SQL for two months (api_execution_gnosis_app_gt_kpi_power_users had lost its `is_registered_active` filter, api_execution_gnosis_app_gt_engagement_tiers ordered by value instead of tier). Keep every file on bare keys.
  The exporter also writes JS escapes raw: `'\\0'` in the source reaches ClickHouse doubled (src/queries/api_consensus_graffiti.js:50; api/queries/api_consensus_graffiti.json:3).
  The id regex is unanchored and case-sensitive, so any earlier key ending in lowercase `id` (for example `uuid:`) would become the id (scripts/export-queries.js:78).
- **`includeFiles` scope.** Keep it at `api/queries/*.json` (vercel.json:10). Widening it to `**` ships the `_disabled/` JSON (src/queries/_disabled/README.md:8-10), which the non-recursive loader then ignores (api/metrics.js:121-124).
  Removing or narrowing it is the real break: it is the only repo setting that names the JSON for the function, `loadQueries` finds the folder only at runtime (api/metrics.js:111,121), and with no JSON it silently serves five demo queries (api/metrics.js:114-117,140-143,156-227), so every real id answers `InvalidMetric` and every card vanishes.
- **Anything named `VITE_*` or `REACT_APP_*` reaches the browser** (vite.config.ts:135). `src/utils/env.js:1-7` hands over the whole `import.meta.env`.
  Never set a ClickHouse credential under those prefixes. Only the unprefixed `CLICKHOUSE_*` names stay server-side (api/cron.js:182-191). `.env.example` templates host, user and password under both browser prefixes (.env.example:2-4,21-23), and `src/utils/config.js:8-12` reads them on the client.
- **The API key is public.** `VITE_API_KEY` (src/utils/config.js:18) is sent from the browser as `X-API-Key` (src/services/api.js:451-457), and the README sets it equal to `API_KEY` (README.md:408). Anyone can call every endpoint.
  `refreshCache=true` re-runs queries against the warehouse (api/metrics.js:346-351). With no id, it runs every query one at a time, each with a 55 s timeout, inside one 60 s function, and then fetches all of them in parallel (api/cron.js:216,261-292; api/metrics.js:378-381).
  With a scoped id, it runs the raw query **unfiltered**, before the `FilterRequired` guard (api/metrics.js:346-349 vs 429-442; api/cron.js:144-157).
  It also stores a 90-day window (api/cron.js:144-154,162-163) under the same key a plain request reads with its 365-day default (api/metrics.js:673-674,737-740), so the queries that use `{from}` (14 of the executed JSON files) serve 90 days from that instance until the TTL. On a cache miss, `useMock=true` stores mock rows under the real cache key (api/metrics.js:714-722).
- **The cache lives in `/tmp`**, per function instance, with a memory fallback and no shared store (api/cache.js:17-32). The TTL is `CACHE_TTL_HOURS` through `parseInt`, so `0.5` becomes 0 and disables caching (api/cache.js:35-37,108-109).
  Empty non-paginated results are never cached, so they hit ClickHouse on every request (api/metrics.js:967).
- **The 60 s function limit** (vercel.json:9) is shared by paths that run several queries in sequence: the circles trust network (api/metrics.js:538,557,730), paginated tables with a total (count, then page: api/metrics.js:826-831,855-862,879), the account counterparty graph fallback (api/metrics.js:879,949-952) and any request carrying `refreshCache=true` (api/metrics.js:346-357). Each query carries its own 55 s timeout (api/cron.js:216).
- **A renamed or dropped dbt model empties a card silently.** A missing-table error becomes `MissingMetricSource` with no log line unless `DEBUG_METRICS=true` (api/metrics.js:980-989,1011). The card then shows a lone em-dash with no Retry (src/components/MetricWidget.js:1260-1275).
  Until the TTL expires, cached rows hide the break (api/metrics.js:703-712). A bad `CLICKHOUSE_DBT_SCHEMA` falls back to `dbt` with only a warning (api/cron.js:14-22). The rewrite is case-insensitive and also touches `dbt.` inside string literals and comments (api/cron.js:33).
- **Scoped-prefix lists differ.** The exporter covers circles group/pool explorer, validators explorer and `api_execution_address_resolver`; the server guard does not (scripts/export-queries.js:16-36 vs api/metrics.js:91-104).
  The exporter always enforces the marker on the validator compare/group/history/profile prefixes and `api_execution_address_resolver`, but on its other prefixes only when the file contains `globalFilterField`; it exempts the two `*_user_top_wallets` ids that the server guard still rejects without a filter (scripts/export-queries.js:38-48; api/metrics.js:95-96).
  The guard only checks that a field and a value were sent: a `filterField` that is not a plain identifier, or a value of only commas, passes it, is dropped, and the query runs **unfiltered** (api/metrics.js:430-433 vs 482-494,664-667,774).
  Without the marker, filters wrap the query and hoist the **last** textual `order by` (api/metrics.js:781-794). That breaks when that `order by` sits inside a subquery.
- **Security headers:** the CSP is `Report-Only` on every path, so nothing enforces it (vercel.json:21,34,47,60). API paths send CORS `*` together with `Allow-Credentials: true` (vercel.json:25-26). `/api/single-value-api` is outside the header rules (vercel.json:19).

## Health is a request, not a green deploy

- **One card:** `curl -s -H "X-API-Key: <VITE_API_KEY value>" "<site>/api/metrics/<id>"`. `<site>` is the production domain, which this repo does not record. The key is the `VITE_API_KEY` value in the Vercel project settings, the same value every browser request already sends as `X-API-Key` (src/services/api.js:451-457). Rows come back as a JSON array; paginated metrics return `{data, page, pageSize, total, lastPage}` (api/metrics.js:842-847,865-870,963-965). Scoped ids need `&filterField=<f>&filterValue=<v>` (api/metrics.js:429-442).
- **Reading the result.** Errors have the body `{error: <code>, message}` (api/metrics.js:400-403). A wrong or missing key gets 401 `Unauthorized` (api/metrics.js:289-295).
  - `InvalidMetric` (400): no JSON was deployed for the id, and the card **vanishes** (src/components/MetricWidget.js:1257-1258). Its `message` lists every id the answering instance loaded (api/metrics.js:419); only the five demo ids there means no JSON was bundled (api/metrics.js:156-227). Text cards have no JSON by design (scripts/export-queries.js:71-75), so do not probe their ids.
  - `MissingMetricSource` (ClickHouse's HTTP status, else 502) or `FilterRequired` (400): an em-dash (src/components/MetricWidget.js:1260-1275; api/metrics.js:1010-1011).
  - `MetricQueryFailed` (ClickHouse's HTTP status, else 502): "Couldn't load" plus Retry (src/components/MetricWidget.js:1260-1286; api/metrics.js:1010-1011).
  - A 200 with `[]` is not an error: the card renders empty, and a number card shows 0, as it does when its `valueField` is missing from the rows (src/components/MetricWidget.js:1298-1299).
  - A YAML id with no `src/queries` file shows a permanent loading skeleton, with no request (src/services/metrics.js:85-86; src/components/MetricWidget.js:1229-1250).
- **Bypassing the cache.** `&useCached=false` forces a query (api/metrics.js:313-317). If that query fails, the unexpired cached entry comes back as a 200 (api/metrics.js:994-1002), so check the warehouse too. Never use `refreshCache=true` as a check.
- **`/api/test`** (same `X-API-Key` header, api/test.js:13-20) reports the cached keys, `lastRefresh`, `cacheTtl`, `clickhouseConfigured` and the effective `dbtSchema`, for the one instance that answered (api/test.js:22-72).
  The keys are cache file names, expired ones included (api/cache.js:278-293). `lastRefresh` moves only on a full warm-up, never on per-request caching (api/cron.js:272; api/metrics.js:968), so null is normal.
- **Use curl, not a browser tab.** In production the browser answers from its sessionStorage copy: under 5 minutes old with no request at all, older while it revalidates behind it, and in place of the error when the request fails (src/services/api.js:4,281-295,318-321,347-350).
- **Warehouse side.** Take the relations from the **executed** SQL in `api/queries/<id>.json`. With read-only access, run `SELECT count(), max(<date column>) FROM <schema>.<model>` and `SELECT name FROM system.tables WHERE database = '<schema>' AND name = '<model>'`, where `<schema>` is the `dbtSchema` that `/api/test` reported.
  Failures other than missing tables, filtered scoped lookups and `api_execution_account_*` ids log `Error fetching metric <id>` to the function logs (api/metrics.js:980-992).

## Rules for agents

- Never assume. Every claim you act on needs a path:line in this repo. Where the READMEs or public docs disagree with the code, the code wins (see the lists above).
- Never run `vercel` in any form that deploys, links or pulls env, and never run git writes (`add`, `commit`, `push`, `checkout`, `stash`, `mv`). Propose the exact commands and let a person run them. `git status`, `git diff` and `git log` are fine.
- After editing any `src/queries/*.js`, run `pnpm run export-queries` and review every changed or pruned JSON before handing over. Never run it as a diagnostic, because it writes and prunes.
  Never write a quoted `"id":` or `"query":` key (the exporter would skip the file and its JSON would freeze). Do not hand-edit any JSON.
- Keep filename == id, one literal `query`, and the filter marker on scoped ids.
- Never widen `includeFiles`. Never put a secret in a `VITE_*` or `REACT_APP_*` variable, or in anything under `public/`.
- Never call `refreshCache=true` or `useMock=true` against production.
- dbt renames and removals are coordinated: the new model lands first, the dashboard moves second, the old model is dropped last.
- This repository is public: no secret values, private hostnames, cluster or project identifiers, IP addresses or personal names in code, YAML, comments or commit messages.

## How a metric becomes a card

1. **Definition** `src/queries/<id>.js`, default export (src/queries/index.js:22-24). Fields in use: `id`, `name`, `description`, `metricDescription`, `chartType`, `isTimeSeries`, `format`, `xField`, `yField`, `seriesField`, `query` (src/queries/api_consensus_staked_daily.js:1-23; src/queries/api_consensus_blocks_daily.js:26-30). Number card: `chartType: 'numberDisplay'`, `valueField`, `changeData` (src/queries/api_consensus_info_staked_latest.js:1-16). Text card: `chartType: 'text'` plus a markdown `content` and no query (src/queries/text_esg_methodology.js:1-6).
2. **Front-end registry**: `import.meta.glob('./*.js')` keys every top-level file by **filename**, not by its `id` field (src/queries/index.js:10-27). `_disabled/` and `__tests__/` are never loaded.
3. **Export**: `pnpm run export-queries` regex-parses the first `id:` and first `query:` (bare keys only) and writes `api/queries/<id>.json` named from the parsed id (scripts/export-queries.js:78-108). Text files are skipped (71-75), unparseable files are skipped with a warning (81-84), and orphan JSON is deleted (119-137). Example output: api/queries/api_consensus_blocks_daily.json:1-4.
4. **Ship**: Vercel bundles top-level `api/queries/*.json` only (vercel.json:10). `loadQueries` keys each file by its JSON `id`, once per cold start in production (api/metrics.js:110-133,229-248). If none load, five built-in demo queries take their place (api/metrics.js:114-117,140-143).
5. **Serve** `GET /api/metrics/<id>`: unknown id → 400 `InvalidMetric` (api/metrics.js:414-423). Scoped prefixes without a filter → 400 `FilterRequired` (91-104,429-442). A valid cache entry is returned first (703-712). `{from}`/`{to}` default to the last 365 days (737-751). Filters replace `/*__FILTER_CONDITIONS__*/` with `AND <conditions>` or wrap the whole query (774-795). ClickHouse runs it (api/cron.js:179-217). Only non-empty or paginated results are cached (api/metrics.js:963-969).
6. **Layout**: `public/dashboard.yml` lists sectors, each with a `source:` (public/dashboard.yml:1-7). The browser fetches that file and takes its `tabs:` (each with a `metrics:` list) or, for a page without tabs, a top-level `metrics:` (src/utils/dashboardConfig.js:76-106; src/services/dashboards.js:102-130). Cards are listed as `id`, `gridRow`, `gridColumn`, `minHeight` (public/dashboards/overview.yml:9-14). Only `id, celoId, gridRow, gridColumn, celoGridColumn, minHeight, tabGroup, tabLabel` survive parsing (src/services/dashboards.js:110-117,180-189). Layout fields override the definition's (src/services/metrics.js:134-139).
7. **Render**: the configs of the active tab's ids (and `celoId`s) are preloaded; ids with no loader are skipped silently (src/components/Dashboard.js:233-236; src/services/metrics.js:85-86). Text cards return `content` without an API call; everything else fetches `/metrics/<id>` (src/services/metrics.js:176-180).
8. **Search**: `build-search-registry` extracts `name`, `description` and `metricDescription` (bare or quoted keys; `metricDescription` capped at 1500 chars) into `public/search-registry.json` (scripts/build-search-registry.js:23-77). The header search walks YAML-placed cards only; the registry just backfills their text (src/utils/metricSearch.js:255-282; src/components/Dashboard.js:652-671). A metric in no YAML is not searchable, and it renders only where the Account Portfolio or Validator Explorer view fetches it by id from code (src/services/accountPortfolio.js:205-218; src/services/validatorExplorer.js:219-275).

## Adding a metric (every step, in order)

**Case A — the dbt model already exists.** Confirm it in the warehouse the site reads before writing anything, with read-only access: `SELECT name FROM system.tables WHERE database = '<schema>' AND name = '<model>'` must return one row, and `DESCRIBE TABLE <schema>.<model>` must list every column the card will map (`xField`, `yField`, `seriesField` or `valueField`). `<schema>` is the `dbtSchema` that `/api/test` reports (api/test.js:22-72); the card's SQL still names `dbt.<model>` (api/cron.js:28-34). The dashboard holds no dbt metadata. Prefer `api_*` models: 42 definitions read `int_*`/`fct_*` models (e.g. src/queries/api_execution_gnosis_app_gt_kpi_power_users.js:9). Treat that as a known exposure, not a pattern.
**Case B — it needs a new dbt model.** First change dbt-cerebro, a separate repository: an `api_*` view tagged `production` (pattern: dbt-cerebro `models/consensus/marts/api_consensus_blocks_daily.sql:1-6`). Merge it, wait until it has built in the production warehouse, then run the Case A check. Only then touch this repo.
A card that ships before its model shows a silent em-dash (api/metrics.js:981,1011; src/components/MetricWidget.js:1260-1275). It fixes itself once the model lands, because failures are never cached (api/metrics.js:967).

Once per clone, run `pnpm install` at the repo root (pnpm-workspace.yaml:1-3) and write the `.env` described under "Local real data". Then, for both cases:
1. Create `src/queries/<id>.js` with **filename == id**: the front end keys by filename (src/queries/index.js:12,21), the API by the exported JSON id (scripts/export-queries.js:107; api/metrics.js:131-132). Five legacy files break this (e.g. src/queries/networkClientDistribution.js:2); copy none of them. Start instead from a copy of src/queries/api_consensus_blocks_daily.js:1-33: bare keys, `id` equal to the filename and to the model it reads, one backtick `query` literal, `export default`.
   A card whose `.js` sets `resolutions: [...]`, placed on a tab with `resolutionToggle: true`, also fetches `<base>_<resolution>` for each listed resolution (`<base>` = the id without `_daily`/`_weekly`/`_monthly`), so every sibling needs its own `.js` and JSON although only one id sits in the YAML (src/components/MetricWidget.js:186-195; src/components/MetricGrid.js:166; src/components/Dashboard.js:245-250). Give every sibling the same `resolutions` and `defaultResolution`, because the toggle buttons come from whichever sibling is showing (src/components/MetricWidget.js:204,236,1094,1134), and place the sibling named by `defaultResolution` in the YAML: the widget shows the YAML id whenever the selected resolution equals `defaultResolution` (src/components/MetricWidget.js:185-195). Example: src/queries/api_execution_gnosis_app_active_users_incl_gpay_weekly.js:18-19 and public/dashboards/gnosis-app.yml:58.
2. Use **bare** keys `id:` and `query:`, with `id:` as the first key. Quoted `"id":`/`"query":` are skipped by the exporter (scripts/export-queries.js:78-84). Make `query` one string literal with no `${}` and no concatenation, because both the exporter and the build-time strip match a single literal (scripts/export-queries.js:79; vite.config.ts:119-122). Reference tables only as `dbt.<model>` (api/cron.js:28-34).
   A text card (exactly `chartType: 'text'`, a `content`, no `query`) gets no JSON: the exporter skips any file that contains that literal anywhere, with single or double quotes (scripts/export-queries.js:71-75), and the front end never calls the API for it (src/services/metrics.js:176-178). So never write that literal in a non-text card's file, not even in a comment or a description: the file would be skipped silently and get no JSON.
3. Scoped ids need `/*__FILTER_CONDITIONS__*/` where `AND <conditions>` belongs (api/metrics.js:774-779). The exporter exits 1 without it for `api_consensus_validator_{compare,group,history,profile}_*` and `api_execution_address_resolver` always, and for the `api_execution_` prefixes `account_`, `circles_v2_avatar_`, `circles_v2_group_explorer_`, `circles_v2_pool_explorer_`, `gnosis_app_user_`, `gpay_user_`, `yields_user_` plus `api_consensus_validators_explorer_` whenever the file mentions `globalFilterField`, except the two `*_top_wallets` ids (scripts/export-queries.js:16-49). The server's `FilterRequired` guard uses a narrower prefix list (api/metrics.js:91-104).
4. Add `- id: <id>` with `gridRow`, `gridColumn`, `minHeight` to a tab's `metrics:` in `public/dashboards/<sector>.yml` (public/dashboards/consensus.yml:7-11). `overview.yml` is the one sector file with a top-level `metrics:` list and no tabs (public/dashboards/overview.yml:9-14). Avoid overlapping cells: a test enforces this (src/services/dashboards.test.js:353-383), but only for grid values written as `N` or `N / span M`; it reads anything else as cell 1 (src/services/dashboards.test.js:354-360). Cards in circles, gnosis-app, governance and hopr also need a `metricDescription` and must sit on exactly one tab (src/services/dashboards.test.js:323,399-416).
5. Run `pnpm run export-queries`. Read the output for `Could not find ID or query`, `Error processing`, `Scoped query export failed` and `Pruned stale query` (the closing `Pruned N stale queries` line always prints), check the exit code (scripts/export-queries.js:82,113,134,137,140-144), and confirm `api/queries/<id>.json` is `{id, query}`. It lands at the top level of `api/queries/`, which `includeFiles` already ships (vercel.json:10), so `vercel.json` needs no change.
   The exporter rewrites every parseable file (scripts/export-queries.js:66-115), so `git status --short api/queries` should list only your JSON; any other diff is someone else's un-exported edit and needs review before handover.
6. Local check: `pnpm dev` with the `.env` above. Open the tab at the local URL Vite prints; the in-process API reads the new JSON immediately (api/metrics.js:235-247). A skeleton that never resolves means the YAML id has no `src/queries` file; a card that vanishes means no JSON (see "Reading the result" under Health).
7. `pnpm exec vitest run src/services/dashboards.test.js src/services/metrics.test.js api` (a full `pnpm test` hangs on `main`, see the commands table). It does **not** check that a placed card has JSON (src/services/dashboards.test.js:348-351). Step 5 is the only guard.
   Its query-file check also reads only tabbed sector files and YAML ids, so it skips `overview.yml`, resolution siblings and ids fetched from code (src/services/dashboards.test.js:331-345).
8. `pnpm build`. It also regenerates the search registry, which is gitignored and rebuilt by Vercel's own build, so nothing search-related is committed (package.json:47; .gitignore:21-22).
9. Hand over to a person: the `.js`, the `.json` (none for a text card) and the YAML committed together on a `feat/` branch, a PR to `main`, and the merge, which deploys. Propose the exact commands and do not run them, for example `git checkout -b feat/<id>`, `git add src/queries/<id>.js api/queries/<id>.json public/dashboards/<sector>.yml`, `git commit -m "feat: add <id> card"`, `git push -u origin feat/<id>`, then a PR to `main`.
10. After the deploy, run the one-card `curl` under Health for `<id>`. A JSON array of rows is success. `InvalidMetric` means the JSON did not ship; `MissingMetricSource` means the model is not in the schema the site reads. The new SQL is live with the deploy, and the cache needs no bust because the key hashes the SQL (api/metrics.js:669-674).

## Removing or hiding a card (every step, in order)

**First, whichever way the id leaves the site (hide, archive or remove), find every reference** with one read-only substring search. It also catches the id under `celoId`, `globalFilterSourceMetric` and `explicitFilterValidationMetric`, and ids written in code:
`grep -rn '<id>' public/dashboard.yml public/dashboards src/components src/services src/utils src/queries/*.js scripts api/*.js`
Every hit outside `src/queries/<id>.js` needs a decision before the id goes. `pnpm test` checks none of the places below, neither of those two tab keys, nor `overview.yml` (src/services/dashboards.test.js:331-351):
- `_daily/_weekly/_monthly` resolution siblings, which are fetched without being in YAML (src/components/MetricWidget.js:188-195). If `<id>` ends in one of those suffixes, run the grep again with the base id. To drop one sibling, delete its files and remove that resolution from the `resolutions:` list of every remaining sibling. If it is the sibling named by `defaultResolution`, also place a remaining sibling in the YAML and point every `defaultResolution` at it (see step 1 of "Adding a metric");
- Landing's hard-coded overview KPI ids (src/components/Landing.js:37-49);
- a tab's global-filter dropdown source: without a `globalFilterSourceMetric` pin it is the first eligible card whose id contains `_total`, else the first eligible card, so removing that card silently changes where the dropdown's options come from (src/components/MetricGrid.js:371-399);
- ids special-cased in the API (api/metrics.js:61-63; api/metrics-pagination.js:1-2) or fetched by the portfolio overview endpoint (api/account-portfolio-overview.js:9-15);
- ids the Account Portfolio and Validator Explorer views fetch from code, many of them in no YAML (e.g. src/components/AccountPortfolio.js:144-166; src/components/ValidatorExplorer.js:469-489; src/services/accountPortfolio.js:205-218; src/services/validatorExplorer.js:219-275).

**Hide (layout only, reversible).** Card: delete its `- id:` block; there is no per-card `enabled` flag (src/services/dashboards.js:180-189). Re-pack the neighbours, which keep absolute grid positions. Its JSON still deploys and still answers `/api/metrics/<id>`, because the API loads every JSON regardless of YAML (api/metrics.js:110-133).
Tab: `enabled: false` on the tab (src/services/dashboards.js:130). Sector: `enabled: false` in `public/dashboard.yml` (src/services/dashboards.js:59; public/dashboard.yml:126-128).
Hidden or commented YAML is still public, because `public/` is served verbatim (src/queries/_disabled/gnosis-pay.celo-layout.yml:3-5). Prefer deletion. Then `pnpm test`, `pnpm build`, and hand over as in step 9 of "Adding a metric".

**Disable the query (archive; the established pattern, src/queries/_disabled/README.md:47-55).**
1. Remove the id from every YAML first. A YAML id whose files sit in `_disabled/` has no loader, so its card stays a skeleton forever (src/services/metrics.js:85-86; src/components/MetricWidget.js:1229-1250; src/queries/_disabled/README.md:14-15), and `pnpm test` fails for tabbed sectors (src/services/dashboards.test.js:348-351).
2. Move `src/queries/<id>.js` to `src/queries/_disabled/` and `api/queries/<id>.json` to `api/queries/_disabled/` (`mv src/queries/<id>.js src/queries/_disabled/` and `mv api/queries/<id>.json api/queries/_disabled/`; plain `mv`, not `git mv`), **both before any export run**. Otherwise the prune deletes the JSON instead of archiving it (scripts/export-queries.js:119-137). Every reader is non-recursive, so `_disabled/` is inert (scripts/export-queries.js:58; src/queries/index.js:10; api/metrics.js:121-124; scripts/build-search-registry.js:46-48; vercel.json:10; src/queries/_disabled/README.md:7-10).
3. Add a why-and-how-to-restore note to both `_disabled/README.md` files (api/queries/_disabled/README.md:10-14).
4. `pnpm run export-queries` (it should prune nothing), `pnpm test`, `pnpm build`, then hand over as in step 9 of "Adding a metric". Restoring runs in reverse: files up first, YAML second (src/queries/_disabled/README.md:14-36). Leave `includeFiles` alone while any `_disabled/` folder exists (src/queries/_disabled/README.md:32-33).

**Remove outright.** Run the checks above, delete the YAML entry, delete `src/queries/<id>.js`, then run `pnpm run export-queries`: the prune removes the JSON (scripts/export-queries.js:119-137), and a test fails on leftover JSON (src/services/dashboards.test.js:385-397). Check that the output says `Pruned stale query <id>.json` and that `git status --short api/queries` lists only that deletion (scripts/export-queries.js:134); any other diff is handled as in step 5 of "Adding a metric". Then `pnpm test`, `pnpm build`, and hand over the YAML edit and both deletions as in step 9 of "Adding a metric".

**When the dbt model goes too: dashboard first, model last.**
1. Find every reader by the **query strings**, never by ids: many ids do not name their table. This read-only search covers `api/queries/*.json` (the executed copy), `src/queries/*.js`, both `_disabled/` folders and the hard-coded SQL in `api/*.js` (api/metrics.js:164,540,559,922,938; api/account-portfolio-search.js:89,117,205,249,291; api/validator-explorer-search.js:101,139):
   `grep -rnEi 'dbt\.<model>([^A-Za-z0-9_]|$)' api/queries src/queries api/*.js`
   The pattern has no leading `\b`: the exporter writes the JSON with `JSON.stringify` (scripts/export-queries.js:108), which stores a newline as the two characters `\n`, so a `dbt.` at the start of a SQL line would follow a word character and fail a word-boundary match.
2. For each hit, remove the card (**Remove outright** above, after its reference checks), archive it only if the model is expected to come back, or repoint its SQL to the replacement and re-export. Hiding is not enough here: a hidden card's JSON still deploys and still runs against the model (api/metrics.js:110-133). A hit in hard-coded `api/*.js` SQL needs a code change to that handler.
3. `pnpm test`, `pnpm build`, hand over, merge and deploy. Re-run the step-1 search: only `_disabled/` hits may remain. Then, with the one-card `curl` under Health, confirm each removed or archived id answers 400 `InvalidMetric` and each repointed card returns rows, not `MissingMetricSource`.
4. Only then drop the model in dbt-cerebro. A **rename** is Case B, then this procedure. Dropping first leaves cached rows for up to `CACHE_TTL_HOURS` per instance (api/cache.js:34-37), then silent em-dashes. The dashboard is only one consumer; the dbt-cerebro side of the check is in "Where the full procedures live".
